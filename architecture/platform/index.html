Viewer platform¶

The same ada library runs behind two server set-ups:

  • Local: a single-process WebSocket server (ada.comms.wsock) that obj.show() starts from any Python script, and that pushes scenes to the viewer as FlatBuffer messages.
  • Hosted: a FastAPI REST service (ada.comms.rest) with a NATS JetStream job queue, a pool of workers, object storage, an optional PostgreSQL database and OIDC login.

Jobs¶

sequenceDiagram autonumber participant B as Browser participant A as REST API participant Q as NATS JetStream participant W as Worker participant S as Object storage B->>A: POST /api/scopes/{scope}/convert (source key, target) A->>A: job_transport.build_transport() alt QueueJobTransport A->>Q: KV put job status = queued A->>Q: publish job_id on ada.viewer.jobs.convert.CAP W->>Q: pull from capability pool W->>S: read source W->>W: formats[kind] → converter / bake / clash …<br/>(optionally in a forked child) W->>S: write _derived/… artefacts W->>Q: KV put job status = done else LocalJobTransport (no NATS) A->>A: LocalJobRegistry starts a job process<br/>(python -m ada.comms.rest.local_runner) A->>S: (job process) read source A->>A: (job process) worker pipeline → formats[kind] A->>S: (job process) write _derived/… A->>A: progress / verdict over the job process's stdout end loop until done B->>A: GET /api/convert/{job_id} A->>Q: KV get status end B->>S: fetch artefacts (presigned URLs)
  • Transport (job_transport.py): QueueJobTransport (NATS) or LocalJobTransport for a set of LOCAL_FEATURES. The light kinds run on threads of the API (asset build/publish, clash check/detail, export selection, plugin jobs, simulation runs, procedural builds). A worker's kinds (conversion, FEA bake / result_meta, utilities, component_build) run in a child process of the same interpreter (local_jobs.start_worker_job → local_runner.py): the worker's own _process_one with no database, a queue that is the child's stdout pipe, and storage reopened from Storage.process_spec(). The child inherits the environment and sys.path and loads the same plugins (plugin_registry.load_local_plugins). Cancel terminates it, and its forked conversion children die with it. A crash is a job error with the tail of its output. A filesystem store's source is linked into the job's temp dir, not copied. Such a server advertises its own conversion matrix, source extensions and utilities (job_transport.local_advertisement, the computation a worker's heartbeat uses), and a conversion it has no converter for is a 501. Every local job, thread or process, passes through one FIFO queue (local_queue.py). It has a cap on concurrent jobs and a CPU budget divided over the running jobs. A job process gets its share as OMP_NUM_THREADS / OPENBLAS_NUM_THREADS / MKL_NUM_THREADS / NUMEXPR_NUM_THREADS / VECLIB_MAXIMUM_THREADS / ADA_STEP_STREAM_WORKERS / ADA_DERIVED_GZIP_THREADS, plus a CPU affinity on Linux when the budget is below the machine. A queued job reports queued (n ahead) and is never started if it is cancelled first. A few sub-second kinds take one extra lane. The limits are settings: routes/local_jobs.py, stored in app_settings or _prefs/_server/local_jobs.json, defaulting from ADA_LOCAL_JOB_PROCESSES / ADA_LOCAL_JOB_CPU_BUDGET and the --max-jobs / --cpu-budget flags. They apply to the next job. Admin audit sweeps (audit_conversion) stay queue-only. The choice is made once at start-up. A queue-less server also answers the procedural blueprint, template and engine catalogs from its own process, and lists engines registered there with origin local (id prefix local:). Its in-process procedural compile takes over root logging and sys.stdout while it runs, which is why it is meant for single-user (desktop) servers. The other procedural jobs on a file-stored model run there too (local_jobs.start_procedural_model_job / start_procedural_import), with the model row the route read handed in instead of read from postgres: the Excel export and import on the API's loop, through the engine registered in this process, a relocation proposal likewise, and the IFC / Genie export in a job process like a conversion (the model row rides in the runner's payload), since it goes through the native writers. An engine says whether it has an Excel format, and which handlers write and read it, through its registration (register_procedural_engine_capabilities( supports_excel=, export_entrypoint=, import_entrypoint=)) or its manifest row; the export/import routes read that, not a list of slugs.
  • Default procedural engine (procedural_default_engine.py): the engine a new model gets when nobody names one. adapy's is the built-in adapy-default; a deployment names another by slug or engine id in ADA_DEFAULT_PROCEDURAL_ENGINE (the viewer image's DEFAULT_PROCEDURAL_ENGINE build arg, the chart's procedural.defaultEngine), and an admin can override it in the procedural_default_engine app setting (Admin > Conversion settings). It is resolved against the engines the scope offers and served as default_engine on /procedural-engines (that engine's summary carries is_default); one not offered falls back to the built-in with a logged warning and a note. Creating a model (POST /procedural-models, /import-xlsx) records it on the row and in the doc unless the caller names an engine (a template names its own), so the Builder opens on it. A commit whose doc names no engine keeps the model's recorded one: stored models are never moved.
  • Queue (queue.py, JobQueue): a JetStream stream with WORK_QUEUE retention. The message body is just the job id. Status and the worker registry live in a KV bucket. Jobs go to capability subjects, so a worker only pulls what it can do.
  • Workers (rest/worker/): loop.py boots, registers and pulls. pools.py has one pool per capability, fetches one job at a time and stops retrying a poison job after a limit. registration.py heartbeats the worker's capabilities (conversion matrix, utilities, clash passes/specs, asset concept providers, simulation providers), gated by qualification.evaluate. routing.py detects misrouted jobs.
  • Job kinds (rest/formats/__init__.py): convert (fallback), fea_artefacts, fea_meta, asset_build, asset_publish, component_build, procedural_* (build, detail, relocations, xlsx import/export, model export, engine build), equipment_bbox, plugin_job, clash_check, clash_check_asset, clash_check_group, clash_detail, clash_detail_group, export_selection, export_selection_asset, simulation_run, utility, parity.
  • Converters (rest/converters/): a (from_ext, to_ext) registry filled by @converter. Families: ada_pairs (passthrough, trimesh, ada-loadable sources), ada_export (GLB, IFC, Genie XML, GNX), mesh_step (STL, OBJ, STEP via OCC), step_stream (native STEP/IFC streams), fea (result decks), pipelines / serializers (tessellation engine options), takeoff (quantity take-off sidecar).
  • Isolation (subprocess_convert.run_isolated_convert): conversions can run in a forked child, so a crash or memory blow-up cannot take the worker down. RSS, CPU and IO are sampled for the audit records.

The REST routes in routes/clash_check.py enqueue clash_* jobs. Workers advertise the passes and connection specs they support (registration.py).

Core has two checkers. adapy ("Member connectivity") is the diagram above: it reads the member model and finds which members are meant to connect (beam axes meeting at a node, beam mid-spans in a plate's padded bounding box, plates edge-on through a CAD distance). It does not measure the solids. convex-contact (convex_contact.py, contacts.py, sidecar.py) measures the viewer GLB's solids with adacpp -- in the browser through its wasm clash module, or on a worker through the same C++ -- and keeps each run as a sidecar beside its model (routes/clash_contacts.py). The viewer's Clashes tab runs convex-contact by default and falls back to adapy, with a note, where it cannot run (state/clashCheck/engine.ts). The same check also runs in process over a member model (mesh_contacts.py: find_member_contacts, find_mesh_contacts), which is what run_clash_check runs when convex-contact is picked and what a connection generator calls instead of keeping a checker of its own. Every path judges its contacts by one set of rules (contact_criteria.py: min_contact_area, min_contact_width_ratio, keep_penetration_depth).

Plugins (ada.plugins)¶

The Python twin of the frontend plugin registry: register_plugin_backend, discover_plugins, plugin_backend_specs, register_plugin_artefact_contributor, request_worker_capabilities, register_preferred_pools, plus external model providers. Plugins are loaded from ADA_WORKER_PRELOAD modules and an entry-point group. rest/plugin_registry.py is the only place the REST side touches the registry.

register_preferred_pools(plugin_id, provider) lets a plugin name the pools its worker should fetch first while it holds something costly to set up for them (an open dataset, a warm session). The worker fetches those pools before the others and keeps its idle pull open on the first of them, so the next job for that pool goes to the worker that is already set up. It only reorders the pools a worker serves, and the streak limit still makes a busy preferred pool give the others a turn.

Scope-gated plugins¶

A plugin can be turned on per scope (shared, projects/<uuid>, users/<sub>) or per user by an admin, instead of being on for everyone. It opts in, and stays OFF everywhere until an admin turns it on under Admin > Plugins (/api/admin/plugin-access, table plugin_access, migration 056). A plugin that does not opt in is never looked up.

Where Declaration
Frontend registration registerPlugin({..., access: "scope"}), or access: {gate: "<id>"} to share one switch between registrations; PropertyProvider.access / CommandSpec.access (a gate id) for what is registered outside registerPlugin
Simulation provider an access_gate = "<id>" attribute on the provider object (advertised as access_gate on its spec)
Backend plugin (jobs) register_plugin_backend(..., access_gate="<id>")
Deployment (optional) the admin-only setting admin.plugin_access.bindings: {"simulation_providers": {"<provider>": "<gate>"}, "plugin_jobs": {"<plugin>": "<gate>"}}, OR-ed with what workers advertise, so an older worker cannot open a gate

The rule for a user working in a scope: the user's own switch decides when there is one (On, or Off, which wins over the scope's On); else the scope's switch; else off. It applies to admins too. The viewer reads GET /api/scopes/{scope}/plugin-access on every scope switch and core hides the gated plugin's slots while it is off. The server refuses a simulation run (and a connections batch start) on a gated provider, and a gated plugin's job, with 403 and the detail {"code": "plugin_access_off", "plugin", "scope", "message"}; switches that cannot be read refuse with 503 plugin_access_unavailable. Without a database nothing is gated: there is nowhere to keep the switches and no admin panel.

Worker pools¶

An idle worker does not walk its pools one blocking fetch at a time. Each round it asks the stream which pools hold messages (one STREAM.INFO request with a subject filter, no lease), fetches from those, then waits about a second on one pool. It still holds at most one leased message. A credential without the stream-info permission falls back to polling the pools in turn.

Where work runs, and what stays on a worker¶

Interactive work runs in the user's browser by default: adacpp's native WebAssembly modules where they can do the job, then Pyodide running the same Python entrypoints a worker runs. The admin execution policy (Admin > Execution, with per-user overrides under Admin > Users) orders the engines per operation (convert, read, fea_bake, procedural_compile, procedural_io, plugin_job, asset_build, core_job). Worker pool access is opt-in per user; the server judges only an explicit choice of the worker over a browser path (X-Ada-Run-On: worker), and refuses a worker job the user's policy does not allow. With every ordinary user's policy set to the browser engines, none of their work needs a worker, apart from the list below.

The FEA bake follows the same rule. A result file (.rmed, .med, .sif, .sin, an exported .sqlite) and a FEM input deck opened in the viewer (.inp, .fem, baked mesh-only) are baked in the browser and the artefact tree is uploaded to /fea/artefacts; the manifest request then finds it stored and queues nothing. A result file's step and field inventory (/result-meta) is read from that same manifest, so it queues nothing either.

Every job a route starts goes through the job transport (ctx.jobs.submit); none is put on the queue directly, so the execution policy and worker access see all of them.

Work that stays on a worker by design, and why:

Work Why it stays on a worker
Asset publish A two-phase publish into the provider store every member reads
Asset change check Reads the provider's source system and writes the change feed
A provider's own plugin job Stages the provider's data for a publish, with the provider's credentials
Selection export of a published node or group Reads attributes and relations from the server's database
The connection builder's build and subject routes The route waits for its job on the server
FEA combinations that re-read raw records (needs_raw recipes, a bake without client-side results) Only the server keeps the raw records
Geometry compare, search exports, sweeps and schedules Administrator and background work across providers or users
Simulations Each provider runs on its own infrastructure (a cluster, a solver licence)

Anything else that reaches a worker for an ordinary user is work still to move to the browser.

Simulations (ada.simulation)¶

A simulation provider is a worker-side object that runs simulations behind one interface, so that a robotics simulator, a second robotics simulator and an FEA solver are three providers and no new plumbing. Core knows no engine: it validates a request, routes the run, hands the provider a context and keeps a record.

sequenceDiagram autonumber participant B as Browser participant A as REST API participant W as Worker (has the provider) participant S as Object storage W->>A: heartbeat: simulation_providers (id, domain, engine, schema, serving) B->>A: GET /api/simulation/providers B->>A: POST /api/scopes/{scope}/simulations (provider, parameters, inputs) A->>A: validate parameters against the provider's JSON Schema A->>S: write _simulations/{run_id}/run.json (queued) A->>W: simulation_run job on the subject of sim-{provider id} W->>W: provider.run(case, ctx) loop while it runs W->>S: ctx.store_artefact(...) → artefacts/{name} W->>A: job status: progress, stage, artefacts_ready B->>A: GET /api/scopes/{scope}/simulations/{run_id} B->>S: fetch a partial artefact (blob route) end W->>S: run.json (done | error | cancelled, artefact list, summary)

The kinds of simulation. A provider's domain is one of a closed set, SIMULATION_DOMAINS:

Domain Required artefact roles Optional
fea result: the solver's result file, in a format the FEA bake reads model: the input deck
robotics model: the animated model (GLB); timeline: the recorded topics over time, in the recording format its media type names (JSON, or a binary recording)
cfd mesh: the result mesh; fields: the field values on it over time

Every domain may also use the common roles log, report and data. A domain carries only what is the same for every engine of that kind, so the viewer can group providers by it and open any provider's result of that kind the same way. The roles are checked while a run is going: storing an artefact with a role that is not the domain's fails the run, and so does finishing without a final artefact for each required role. The engine (the simulator's or solver's name) is free text and core never reads it.

Writing a provider. A provider has an id (lower-case letters, digits, -, _), a domain, an engine, describe() and run():

from ada.simulation import ProviderDescription, SimulationResult, register_simulation_provider

class BeamSolver:
    id, domain, engine = "beam-solver", "fea", "an FEA solver"

    def describe(self):
        return ProviderDescription(
            title="Beam solver",
            version="1.0.0",
            parameters_schema={
                "type": "object",
                "properties": {"load_factor": {"type": "number", "minimum": 0, "default": 1.0}},
            },
        )

    def run(self, case, ctx):
        deck = ctx.fetch_input(case.inputs[0])          # an input file, streamed to local disk
        for step in range(10):
            ctx.raise_if_cancelled()                    # cooperative cancel
            ctx.progress(step / 10, f"increment {step}")
            ctx.log(f"increment {step} converged")
        out = ctx.workdir / "beam.rmed"                 # ... the solver wrote this
        return SimulationResult(
            artefacts=(ctx.store_artefact("beam.rmed", out, role="result"),),
            summary={"increments": 10},
        )

register_simulation_provider(BeamSolver())
Piece What it is
SimulationCase run_id, the scope, the parameters (validated, with the schema's defaults filled in), the input keys and the kind of run.
SimulationContext progress(fraction, stage), log(line), cancelled() / raise_if_cancelled(), store_artefact(name, data_or_path, *, partial=False, role=..., media_type=...), read_input(key) / fetch_input(key) and a scratch workdir.
SimulationResult The artefacts the provider calls final (as store_artefact returned them) and a small summary dict.
store_artefact(..., partial=True) Puts the artefact in storage and on the run at once, to be replaced under the same name later: a viewer follows a run through these, as it follows the FEA bake through artefacts_ready. Each store raises the artefact's revision.

The parameter schema is JSON Schema; the part that is checked (types, enum, numeric and length limits, required, additionalProperties, items, default) is in ada/simulation/schema.py.

Registering. register_simulation_provider is also exported from ada.plugins, and a provider's module is loaded like any plugin backend: listed in ADA_WORKER_PRELOAD, or reached through an ada.plugins entry point. Registering asks the worker for the capability sim-<provider id> through request_worker_capabilities, so it passes the same qualification and ADA_WORKER_DISABLED_CAPABILITIES switch as any other capability. The heartbeat lists each provider with its description and whether this worker serves it.

Routing. There is one job kind, simulation_run (rest/formats/simulation.py), published on the provider's capability subject, so only a worker that registered the provider pulls it. A job that still reaches a pool without the provider is failed at once with a reason naming the provider (worker/routing.py). POST .../simulations refuses a provider no live worker serves (409) and an unknown one (404) before anything is queued. Without NATS, LocalJobTransport runs a provider registered in the API process in a thread; both paths call ada.simulation.runner.execute_run, so a provider cannot tell which it runs under.

What a run stores. A run is a directory in the scope it was started in:

Key Content
_simulations/{run_id}/run.json The run record: provider (id, domain, engine, version), kind, parameters, inputs, who started it, created_at / started_at / finished_at, status, stage, progress, error, job id, the artefact list and the summary.
_simulations/{run_id}/artefacts/{name} What the provider stored. Each is listed with name, key, media_type, role, size, partial and revision, and fetched through the blob route.
_simulations/{run_id}/cancel Present once a cancel was asked for.

The record is a JSON manifest beside the artefacts, as clash runs are documents in storage: it needs no database, it is written before the job is published, and it outlives the job status, which the queue forgets soon after the job ends. Run ids sort by creation time, so the newest runs come from one directory listing. Being under _derived/, a run cannot be written through the blob route, and "clear temp files" removes it. Cancelling is cooperative: the marker is what a provider's ctx.cancelled() finds, in whichever process runs it. A run whose job failed without finishing the record, or whose job the server no longer knows, is ended with that reason the next time it is read.

Route Does

POST /api/scopes/{scope}/simulations Start a run: {provider, parameters?, inputs?, kind?} → {run}.
GET /api/scopes/{scope}/simulations The scope's runs, newest first (limit, provider, domain).
GET /api/scopes/{scope}/simulations/{run_id} One run, with the live job's progress and artefacts laid over the record.

In the viewer, the Simulations panel (core:simulations) lists providers by domain, builds a start form from the parameter schema and lists runs with their artefacts. A frontend plugin adds what core cannot know through simulationProviders in the plugin registry: a parameter form section and an "open result" handler, registered for one provider id or for a whole domain.

A run's console. A run has actors -- a robot, an arm, a solver stage, the mission that directs them -- and a provider that wants its run understood, not just watched, says what each is doing and planning as the run goes. That is the artefact with the role activity (a common role: any domain may have one): an activity feed, JSON Lines, append-only, stored again while it grows (partial=True). ada.simulation.activity has the format and a writer:

{"schema": "ada-activity/1", "actors": [{"id": "amr", "label": "Logistics robot", "color": "#4db3e6"}]}
{"t": 0.2,  "actor": "amr", "kind": "state", "text": "Driving into the cell", "data": {"goal": [-0.59, 1.92, 0.35]}}
{"t": 0.2,  "actor": "amr", "kind": "plan",  "text": "Dock beside the picker"}
{"t": 13.4, "actor": "amr", "kind": "event", "text": "Docked 23 mm off its dock", "level": "info"}

t is seconds on the run's own clock (the one its recording and its model's animation are on); a state is what the actor is doing from then on, a plan what it intends (an empty text: none), an event something that happened. The viewer reads the feed itself -- no plugin is involved -- from the moment a run's result is opened in the Simulations panel, asking for the bytes beyond those it has while the run is going (state/runConsoleStore.ts). The playback transport then has a Console button: a panel over the view with a row per actor (what it is doing and planning at the playback clock's moment) and the log up to that moment, where a click on a line goes to it. It is the same console for a replay and for a live run.

What a run is on: subjects. A simulation of a part with welds needs that part, and the thing that made the part (the connection studio, a detailing engine) is not the thing that simulates it. Core sits between them and they never name each other. A subject is a file in the scope of a kind core defines (ada.simulation.subjects.SUBJECT_KINDS, a closed set like the domains). The one kind so far is weld-assembly: a part with its welds assigned -- its members as closed triangle meshes, and each weld's root line with the two face normals at the seam -- as JSON of schema ada-weld-assembly/1 (metres, +Z up, origin under the part; gzip allowed), or ada-weld-assembly/2 once a seam is curved or closed (a tubular joint's saddle weld runs round the brace): every weld then carries closed and, per point of its line, tangents, normals_a and normals_b, a straight seam being the two-point case with one tangent and the same normals throughout. The writer keeps to /1 while every seam is straight, so a reader of /1 only ever refuses a curved seam rather than taking it for a line from its first point to its last; weld_seam(weld) gives a weld of either as the per-point form. A curved seam's line is the weld's sweep curve (an arc sampled every 10 mm / 10 deg), its normals the members' surfaces at each point (from their meshes, else from the profile's direction). A producer builds it with weld_assembly_from_part(part, members=None, stub_length=None, source=None) (members= for a part whose welds name members that live elsewhere, stub_length= to cut long beams back to the welds) and stores it with write_weld_assembly; a consumer reads it with parse_weld_assembly, which validates it.

  • A provider says which kinds it takes: ProviderDescription.accepts, listed with the provider (GET /simulation/providers, and in the worker's heartbeat) as accepts: [...].
  • A run is started on one: POST /scopes/{scope}/simulations takes subject: {kind, key}. The kind must be known and accepted by the provider (400), the file must exist (404) and not be mid-upload (409). Its key is put first among the run's inputs and the record keeps subject; the provider finds it as case.subject (a SubjectRef) and reads it with ctx.fetch_input(case.subject.key).
  • In the viewer, a producer offers a subject: a plugin calls ctx.simulations.offerSubject( {kind, key, label, scope?, source?}) (plugin API 1.21.0; it returns {withdraw}), core chrome uses useSimulationSubjectStore. The Simulations panel then shows a Subject picker (the newest offer chosen, or "(none)"), lists the providers that accept its kind first and says "does not take a <kind>" against the rest, starts the run in the subject's scope with subject in the body, and names the subject on the run's row.

The Simulations panel's Refresh asks for the scope's runs and the providers again: the panel follows the runs it knows are unfinished, and a run started elsewhere since it was opened (another tab, the API) is only found by asking. Audit and issue bot¶

Every conversion leaves an audit row: its outcome, conversion provenance and the profiler summary parsed from the child process log (worker/audit.py). On a queue-less server with a database the job process has no database, so the server records the outcome itself when the job ends: status, error and run time (routes/deps.py audit_local_job_outcome), without the provenance and profiler summary. Admins schedule audit runs on a cron (routes/admin_audit_schedules.py, fired by the scheduler background task) and inspect runs and performance (admin_audit_runs.py, admin_audit_perf.py). audit_issue.py fingerprints failures and files or updates issues on GitHub or Forgejo (issue_client.py). The ada audit … CLI commands fetch and reproduce runs.
